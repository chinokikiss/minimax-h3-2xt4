# H3 DiT P0-B — Physical Dual-T4 Final Report (2026-11-02)

## Verdict

**P0-B passes actual dual-T4 bitwise-accuracy and allocated-memory qualification on both studied long sequences. It does not yet pass the user's strict performance non-regression gate. Keep P0-B experiment-only; do not enable it in production.**

- **Accuracy:** Both physical T4 ranks report **zero raw-bit mismatches** in FC2 INT8 codes and FP32 row scales at S=128, 6,814, 59,134 and 65,166. Both trained DiT block-0 final FP16 outputs are **bit-exact** at S=59,134 and 65,166. No non-finite outputs were reported.
- **Real FC2 stage memory:** `max_memory_allocated` improves by **1.190 GiB** at S=59,134 and **1.312 GiB** at S=65,166 on **each** T4.
- **Real trained-block memory:** With exactly equal before-call live allocations in both arms, observed whole-block allocated peaks improve by **0.597 GiB** and **0.503 GiB**, respectively. This is a substantially smaller saving than the FC2-local saving because other stages become limiting.
- **Warmed block performance:** At S=59,134, P0-B is **0.93% slower** by the slower-rank median; all nine paired comparisons were slower on both ranks. At S=65,166, the slower-rank median is **0.80% faster**, with substantial drift and only six of nine paired comparisons faster.
- **Scope:** Real, trained, **single-block** dual-T4 run with true NCCL reduction and production P0-A1/P0-C/P0-2/P0-3 controls left on in both arms. It is **not** full-H3 25-shard denoising E2E or a universal-shape proof.

## PyTorch Allocated Peak: real memory gains

Values are **GiB (2^30 bytes)**. Both ranks returned the same allocated peaks. Baseline and experimental arms had identical phase-entry/whole-call live allocated bytes; the whole-call peak was repeated twice per variant with exactly the same result.

| Measured memory scope | S=59,134 baseline | S=59,134 P0-B | Reduction | S=65,166 baseline | S=65,166 P0-B | Reduction |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| FC2 phase peak | 4.576 | 3.386 | **1.190** | 5.023 | 3.711 | **1.312** |
| Whole trained-block peak | 4.576 | 3.979 | **0.597** | 5.023 | 4.520 | **0.503** |
| FC1 phase peak | 3.879 | 3.879 | **0.000** | 4.255 | 4.255 | **0.000** |

The matched memory baselines are:

- **S=59,134:** FC2 phase entry **2.990 GiB** in both arms; whole-call initial allocated **0.818 GiB** in both.
- **S=65,166:** FC2 phase entry **3.275 GiB** in both arms; whole-call initial allocated **0.881 GiB** in both.

Thus the core prediction is verified: reusing the equally sized FC1 FP16 allocation for remapped FP32 activations eliminates the independent rotated allocation during the FC2 preparation and lowers real FC2 stage peak. The **full-block gains are only 0.597/0.503 GiB**, not 1.190/1.312 GiB, because the maximum shifts to another live workspace. These must not be described as full-H3 E2E reductions.

These figures use `torch.cuda.max_memory_allocated()`, **not** driver-used memory or `max_memory_reserved()`.

## Warmed dual-rank CUDA timing

Nine paired A/B repetitions per shape, after compilation and three warmups; no new compilation requests were observed during timed samples. **Important benchmark-order limitation:** the reused `balance()` helper's two-variant shift-plus-reverse schedule actually runs **baseline first, P0-B second in every pair**, rather than reversing their order. This can bias sub-1% comparisons and must be corrected in a follow-up. Negative percent means faster. Show the **slower rank's median** so dual-GPU execution is not misreported as a sum.

| Geometry / attention | Baseline median | P0-B median | Relative change | Timing verdict |
| --- | ---: | ---: | ---: | --- |
| S=59,134 / Kitchen | **2,430.09 ms** | **2,452.67 ms** | **+0.93% slower** | **Fails strict no-regression** |
| S=65,166 / Sol-v2 | **2,533.36 ms** | **2,513.09 ms** | **−0.80% faster** | Favorable median; mixed samples |

For S=59,134, **all 9/9 paired samples on both ranks** ran slower with P0-B; the paired median penalties were **11.37 ms (rank 0)** and **11.24 ms (rank 1)**. The median-to-median difference is larger (**22.59 ms**) because the samples drift throughout the interleaved sequence. The sign is consistent throughout this fixed-order run, but it **cannot be separated from systematic ordering bias**. It is not evidence of guaranteed zero cost or a statistically isolated intrinsic penalty.

For S=65,166, **6/9 paired samples were faster** with P0-B on each rank, and 3/9 were slower; the paired median gain was about **14.3 ms**. Timings drift from roughly **2.46 to 2.76 seconds**, much larger than the sub-1% aggregate margin. These observations do not establish a robust performance win.

The block timing includes attention, norm/gate, QKV, FC1, FC2, communication and fused residual; it is not merely the standalone quantizer latency. Earlier local RTX 5060 Ti (SM120) quantizer-only timing results cannot substitute for these T4 observations.

## Production decision and next validation

| Gate | Observed | Decision |
| --- | --- | --- |
| Actual dual-SM75 dispatch / package identity | Pass | Qualified for studied environment |
| Real TP2 INT8 codes and scales | 0 bit differences | Pass |
| Trained-block output | 0 bit differences | Pass |
| FC2 / whole-block Allocated Peak | Verified material savings | Pass |
| Strict performance non-regression | **S=59,134 +0.93% slower** | **Not passed** |
| General untested shape / full-H3 E2E | Not exercised | Not certified |

**Hold P0-B outside the production runtime.** It is a promising memory optimization, but the present result does not permit a blanket 100%-exact and 0%-performance-cost claim across all production workloads. The fixed within-pair timing order further prevents a rigorous intrinsic speed comparison, even though both raw medians and paired samples are retained.

If the user wants promotion under the original no-degradation rule, first replace the fixed-order two-variant timing schedule with true randomized/balanced crossover timing, investigate the observed S=59,134 penalty, and repeat dual-T4 timing with sufficient samples and a separately qualified full-H3 long-sequence E2E allocated-peak comparison. Keep the original P0-3 fast fallback and the strict Tensor-owner/LoRA/SM75 guards. No default was changed by this verification.
